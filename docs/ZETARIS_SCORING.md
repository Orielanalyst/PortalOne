# Zetaris evaluation: ReliefIntel proof and reflection

**Use case:** turn fragmented pre-intervention information into an inspectable mission context before an agent proposes action. A community reference, a warehouse balance and an access record have different owners, keys and validity periods. Joining them correctly is the product's data foundation.

This document follows the supplied **Build with Zetaris evaluation criteria**. It distinguishes executed work from proposed product improvements and projected benefits.

## 1. Build and verify the Unified Semantic Layer

### Three registered sources

| Logical Zetaris source | Contents used here | Why it matters | Exploration |
|---|---|---|---|
| `PORTALONE_COMMUNITY_V1` | Public OSM community references and the explicitly synthetic community-to-depot association | Reconcile the named community to a stable place ID; avoid joining on a spelling alone | Community/revision count; linked-community lookup |
| `PORTALONE_LOGISTICS_V1` | Synthetic warehouse inventory and fleet availability in PostgreSQL | Resolve stock and vehicle capacity before planning | Stock/expiry by depot; available fleet by depot |
| `PORTALONE_SCENARIO_V1` | Synthetic route-segment JSON registered as Lightning file tables | Aggregate route distance, time, weight bottleneck and expiry in the engine | Route totals; simulation/expiry inventory |

These are **three logical registered sources**, not three independent physical systems: the first two are separate schemas/read roles on the same owned rehearsal PostgreSQL instance; the third reads registered JSON files. The community schema also supports the application's Kobo projection, but this public scoring proof reads **no report records, private batch metadata or narratives**. Public humanitarian context is a separate application retrieval path and is not claimed as a fourth USL source.

All **six exploratory SELECTs**, four activation SELECTs, three verification SELECTs and two custom DQ expressions are in [queries.json](../data/zetaris-usl-v1/queries.json). Actual outputs are in the [Zetaris receipt](evidence/zetaris-usl-2026-10-27.json).

### One deployed USL, with DDL and keys

**Model:** `lightning.metastore.portalone.mission_intelligence_v1`

[Complete executable DDL](../data/zetaris-usl-v1/model.sql) defines four semantic tables:

- `communities`: one row per public place ID, retaining the acquired map revision.
- `depots`: stock/fleet aggregation by depot, retaining stock expiry and simulation status.
- `community_logistics`: the explicit community-to-depot association, with foreign keys to community and depot.
- `route_options`: segment aggregates per synthetic route, with a foreign key to the starting depot, expiry and simulation status.

The operator CLI compiles/deploys an absent model and activates each table against its registered source query. A second execution reuses the model and validates activation again; it never removes a model or changes source records. The fresh local catalog required creation of the `lightning.metastore` parent before the project namespace. No platform sample was reset.

**Executed verification:** the activation catalog returns **four active tables**; the USL returns **16 public community references**; the joined mission-context query returns **two synthetic route options** for Bambili, with **120 rehearsal kits and two available rehearsal vehicles**. These are demo inputs, not assets available to an NGO. The third query retains expiry and reports both route options as no longer current.

The direct and detour values (20/30 km, 40/60 minutes, 3,500/6,500 kg bottlenecks) are **synthetic route arithmetic**, not the road geometry generated by the application's real map tools and not field clearance. The distinction is retained in the receipt.

### Data quality executed, including a meaningful failure

| Custom rule | Executed outcome | Meaning |
|---|---|---|
| `nonnegative_rehearsal_capacity` | 1 evaluated, 1 valid, 0 invalid | The rehearsal depot has nonnegative stock/vehicle counts and remains explicitly synthetic. |
| `current_access_evidence` | 2 evaluated, 0 valid, 2 invalid | Both route options expired on 24 October. They must not support current access decisions. |

The freshness failure is a useful result: available data is not necessarily decision-ready data. Neither a successful SQL query nor a passing structural rule establishes that a road is passable.

### Reproduce

Requires the already provisioned local Zetaris services, registered rehearsal sources and operator credentials in `.env`:

```powershell
bun scripts/check-zetaris-usl.ts          # Show scope without executing writes
bun scripts/check-zetaris-usl.ts --apply  # Deploy/reuse, activate, explore, query and run DQ
bun scripts/compare-zetaris-usl.ts        # Compare the same result with manual joins
```

Uses the existing [authenticated Zetaris client](../src/lib/server/zetaris.ts). Provisioning is an operator operation, never a tool that an LLM can invoke. New receipts stay under ignored `.runtime/usl` until reviewed for publication.

**Application boundary:** the running application's live report federation still uses its fixed, bounded source-level SELECT templates in [community-evidence.ts](../src/lib/server/community-evidence.ts). This USL is an additional deployed and verified semantic contract; the live report adapter has not been migrated to it. The existing engine already resolves report/logistics joins before model reasoning. The published custom DQ runs are proof of execution, not a claim that these two rules currently gate every application call.

## 2a. What the USL saves versus application joins

Without a shared semantic layer, application code must fetch fragments, group segments, match depot IDs, total stock and vehicle availability, normalize returned types, preserve simulation flags and propagate the most restrictive expiry. Every additional consumer can repeat those definitions differently.

The USL centralizes those meanings and relationships in executable DDL and activation queries. A caller requests the compact mission context rather than embedding the same integration in its prompt or code. This is why Zetaris is foundational to ReliefIntel: the agent needs a resolved evidence basis, not a pile of unrelated tables.

We implemented a small [manual baseline](../scripts/compare-zetaris-usl.ts) and executed both approaches against the same sources. The [comparison receipt](evidence/zetaris-usl-comparison-2026-10-27.json) confirms **identical normalized results**:

| Observation | Manual application joins | USL query |
|---|---|---|
| Source requests made by this caller | 4 | 1 |
| Rows crossing into this caller | 8 | 2 |
| Place/depot/route matching and aggregation | Application code | Zetaris activation definitions/query |
| Observed local elapsed time, one run | 942 ms | 1,401 ms |

This observation demonstrates less application-side integration and a smaller returned result, **not a query-speed advantage**. It is one sequential local sample with different cache/warm-up conditions. No staff-time or token savings percentage is claimed as measured. The USL implementation also required real integration work: namespace setup, type-compatible activation expressions and DQ verification. Our project benefit is reusable definitions and less repeated application logic; an NGO pilot must measure operational time saved.

## 2b. Where the USL helps in NGO work

For a relief coordinator, the valuable question is “which communities have needs that our verified resources and access evidence can support?” It crosses field collection, geography and operations. A reusable semantic contract lets the team ask that question repeatedly as inputs change, rather than rebuild the integration for every planning meeting.

It helps when stable source ownership, useful keys and queryable endpoints exist. It does not create missing observations, reconcile an ambiguous village by certainty, verify a reporter, remove connectivity constraints or replace local access confirmation. A small one-off CSV task may not repay semantic-model setup.

**Forecast example — monthly mobile-clinic preparation:** assume a team currently spends 6 hours per cycle reconciling field submissions, facility lists, warehouse sheets and access updates. Assume 3 hours remain for source verification and review after reusable joins/quality checks, plus 12 hours of initial setup. That would save **3 hours per cycle** and break even after **four cycles**. These are planning assumptions, not customer measurements. A pilot would log preparation time, corrections, missing inputs and review outcomes over at least four cycles before claiming a benefit.

## 2c. PM requirement: evidence-qualified semantic answers

**Problem:** a structurally valid answer can combine expired access evidence, synthetic resource balances and ambiguous place matches. Consumers need more than a successful SELECT to know whether that answer is fit for a decision.

**Proposed capability: an evidence contract attached to a USL query.** Let a model author bind source-row identifiers, observation/expiry columns, simulation policy, location-match status and required DQ rules to semantic fields. Return a machine-readable qualification envelope alongside the bounded result.

**User story:** as a mission coordinator, I can inspect why an answer is held, which source rows caused the hold, and what must be refreshed without reconstructing the joins in my application.

**Acceptance criteria:**

1. An author declares freshness and provenance requirements once per USL table/relationship.
2. Query results preserve row-level origin references and the quality-rule execution timestamp.
3. Expired, synthetic, ambiguous and missing values are distinguished; none is silently converted to “verified.”
4. Missing sources and failed rules produce an explicit qualification state and actionable gap list.
5. A model revision and its activation/quality evidence can be published atomically, preserving the prior revision for audit.
6. A consumer can request compact qualified results without receiving source narrative or credentials.

**Mock result for the actual rehearsal context** — proposed envelope, not an implemented Zetaris command:

```json
{
  "model": "mission_intelligence_v1",
  "qualification": "hold",
  "rows": 2,
  "evidence": {
    "sources": ["PORTALONE_COMMUNITY_V1", "PORTALONE_LOGISTICS_V1", "PORTALONE_SCENARIO_V1"],
    "failedRules": ["current_access_evidence"],
    "invalidAccessOptions": 2,
    "resourceMode": "synthetic"
  },
  "requiredActions": ["Obtain current access confirmation", "Replace rehearsal logistics with an authorized current ledger"]
}
```

The resulting semantic contract would retain the current four tables and add qualification metadata to `depots` and `route_options`: source references, expiry policy and required rule IDs. The mock changes the consumer response and publication contract; it does not pretend to be supported SQL syntax today.

Official command syntax was checked against [Zetaris's command reference](https://github.com/zetaris/getting-started/blob/main/docs/guides/zetaris-lightning-sql-commands.md), then verified against the running local engine. The submitted receipt contains actual responses, not documentation examples.
